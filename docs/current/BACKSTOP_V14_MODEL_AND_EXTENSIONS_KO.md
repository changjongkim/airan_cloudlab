## 1. 복구 손실 모델

### 1.1 모델

- NRx N개가 약한 셀 W개의 후보를 처리한다. UL 슬롯은 P = 2.5 ms마다 온다.
- 슬롯 k의 후보는 kP + c에 알려지고(c: 기존 수신기 완료, 중앙값 1.35 ms), kP + L까지 NRx를 시작해야 한다.
  L = 복구 마감 − NRx 시간 한도 = 11.5 − 7.6 = 3.9 ms.
- NRx 실행은 혼자일 때 S0(중앙값 6.28 ms), AI 옆에서 S1(낮은 우선순위·한도 없음 7.97 ms)이 걸린다. 실행 중 일부만
  AI와 겹치면 그 구간만 S0/S1의 속도로 진행한다.
- L까지 빈 NRx가 없는 후보는 버려진다(기다릴 수 없는 손실 시스템).

**핵심 식.** 슬롯 k의 오프셋 s에서 시작한 실행이 슬롯 k+m의 후보를 받을 수 있는 조건은 `s + S ≤ mP + L`이다.
따라서 그 NRx가 붙잡히는 슬롯 수는

```text
h = ceil((s + S − L) / P)
```

P = 2.5, L = 3.9, s = 1.4에서 S = 6.3 ms면 h = 2, S > 7.5 ms면 h = 3이다. **AI가 복구를 잃게 만드는 경로는 NRx의
마감 초과가 아니라 h가 2에서 3으로 바뀌는 것**이다. 낮은 우선순위 AI 옆의 실행(7.6–8.0 ms)은 전부 h = 3이 된다.

모델의 두 가지 계산:

| 계산 | 입력 | 용도 |
|---|---|---|
| 사건 모의 (`loss_model.simulate`) | 후보의 도착(슬롯, 알려진 시각), N, L, P, S0, S1, AI 규칙, 중단 지연 | 규칙을 주면 손실을 예측, 규칙 선택 |
| 닫힌 형태 (`loss_model.chain_markov`) | N, 슬롯당 후보 수의 전이 행렬 T, 3슬롯 실행의 비율 f | 도착 통계와 f만으로 손실을 계산 |
| 닫힌 형태, f를 계산 (`loss_model.lane_chain`, 1.7절) | N, T, 후보가 알려지는 시각 c의 분포, NRx 실행 시간 S의 분포 | f를 재지 않고 손실과 f를 계산, 민감도 |

닫힌 형태는 Markov chain이다. 상태는 (1슬롯 더 붙잡힌 NRx 수 n1, 2슬롯 더 붙잡힌 NRx 수 n2, 이번 슬롯의 후보 수 a)다.

```text
이번 슬롯에 서비스되는 후보   s = min(a, N − n1 − n2)        버려지는 후보   a − s
s개 중 3슬롯 실행의 수        j ~ Binomial(s, f)
다음 상태                     (n2 + s − j,  j,  a')          a' ~ T[a, ·]
손실률                        E[a − s] / E[a]   (정상 분포에서)
```

- T[a, a']는 "이번 슬롯의 후보가 a개일 때 다음 슬롯의 후보가 a'개일 확률"이다. AI 없는 실행에서 잰다.
  같은 셀의 실패는 이어지는 슬롯에 몰린다(후보가 난 셀이 다음 슬롯에도 후보를 낼 확률 0.19–0.26, 평균 0.145).
  이 의존을 빼고 독립(Binomial)으로 두면 손실을 절반 이하로 본다(1.2절).
- f는 방식이 정한다. AI 없음 0.07–0.09, NRx 옆 금지 0.11, lane 여유 3은 0.33–0.35, 여유 2는 0.59–0.64,
  낮은 우선순위 + 30% / 70%는 0.29 / 0.85.
- **방식의 차이는 f 하나로 요약된다.** 같은 도착에서 f = 0.08 → 1.4%, 0.35 → 2.7%, 0.85 → 5.3%(NRx 4개, 약한 셀 4개).

### 1.4 모델이 알려 준 것

규칙별로 "버려지는 후보 / AI가 돌 수 있는 GPU 시간 비율"을 계산했다(N = 4, W = 4, 시드 1의 도착).

| 중단 지연 | NRx 옆 금지 | lane 여유 3 | lane 여유 2 | lane 여유 1 | 재사용 시각 규칙 | 항상 |
|---|---|---|---|---|---|---|
| 0 ms | 4.3% / 0.62 | 4.3% / 0.70 | 4.3% / 0.80 | 5.8% / 0.89 | 5.6% / 0.83 (지연 0.5) | 8.8% / 1.00 |
| 0.5 ms | 4.6% / 0.64 | 4.6% / 0.72 | 4.6% / 0.82 | 6.4% / 0.91 | 5.6% / 0.83 | 8.8% / 1.00 |
| 2.0 ms | 5.7% / 0.71 | 5.7% / 0.79 | 6.5% / 0.88 | 7.8% / 0.95 | 8.8% / 0.89 | 8.8% / 1.00 |

1. **중단 지연이 손실을 정한다.** AI를 멈춰야 할 때 실제로 멈추기까지의 시간이 2 ms면 "NRx 옆 금지"도 5.7%를
   잃고, 0이면 4.3%다. v13은 조각이 끝날 때까지 멈추지 못했다(중앙값 2.3 ms, p99 8.7 ms).
2. **lane 여유 3까지는 손실이 늘지 않는다.** 지연이 작으면 여유 2도 같다. 여유 1은 1.5–2%p를 더 잃는다.
   "왜 3인가"의 답: NRx 4개에서 혼자 도는 NRx를 늦추는 것은 다음 후보가 다른 NRx를 쓰므로 손실이 없고, 둘 이상이
   돌 때 늦추면 3슬롯 붙잡힌 NRx가 겹쳐 후보가 버려진다.
3. **AI가 기존 수신기를 늦추는 것만으로 0.4%p를 잃는다.** 후보가 0.33 ms 늦게 알려져 NRx가 늦게 시작한다.
4. **"재사용 시각까지의 여유를 AI에 쓰는 규칙"은 N = 4에서 손해다.** 여유를 다 쓰면 그 NRx를 기다린 다음 후보가
   늦게 시작해 연쇄로 3슬롯 실행이 된다. N = 1에서는 손실 없이 AI 시간이 0.64 → 0.82로 는다.

### 1.7 3슬롯 실행의 비율을 계산하는 닫힌 형태

1.1절의 닫힌 형태는 3슬롯 실행의 비율 f를 실행에서 재야 했다. `loss_model.lane_chain`은 f를 계산한다.

**구조(실측).** 16셀·약한 셀 4개에서 NRx 실행의 약 8%는 빈 NRx가 없어 NRx가 풀리기를 기다렸다가 시작하고, 그
93%가 3슬롯 실행이다. 빈 NRx에서 바로 시작한 실행은 `P(c + S > 2P + L)`의 확률로 3슬롯이 된다. 따라서 f는
"c와 S의 분포"와 "기다린 실행의 비율"에서 나오고, 뒤의 것은 chain의 상태에서 나온다.

**상태.** NRx마다 다음 중 하나다.

| 상태 | 뜻 |
|---|---|
| idle | 비어 있음 |
| J2 / J3 | 2슬롯 / 3슬롯 이상 실행이 이번 슬롯 안에 끝남 (풀리는 시각의 분포 φ2 / φ3) |
| A1 | 이번 슬롯은 붙잡혀 있고 다음 슬롯에 J2 |
| B1, B2, B3 | 1, 2, 3슬롯 더 붙잡혀 있고 그 뒤 J3 |

```text
후보의 배정 순서     idle → J3 → J2          (J3는 슬롯 초반에 풀린다)
시작 시각            idle: s = c            J2, J3: s = max(c, 풀리는 시각)
붙잡는 슬롯 수        h = ceil((s + S − L) / P)      풀리는 시각 = s + S − hP
버려지는 후보        이번 슬롯의 후보 수 − (idle + J3 + J2)
```

φ2, φ3과 chain의 정상 분포를 번갈아 계산해 고정점으로 수렴시킨다(6회). 상태 수는 NRx 4개에서 210 × 후보 수다.

**입력.** N, 전이 행렬 T(AI 없는 실행), c의 분포, S의 분포. c와 S는 같은 조건·같은 방식의 다른 시드에서 잰
분포를 쓴다(예측 대상 실행의 값은 쓰지 않는다. 시드가 하나뿐인 설정 2개는 그 실행의 값).

### 2.4 결함 3: 가장 큰 AI 단위가 기존 수신기를 늦췄다

## 3. 복구를 사용자 지표로: UL goodput, 재전송, 지연

### 3.1 계산 방법

실행이 남긴 TB별 기록(기존 수신기 성공 여부, NRx 시작 여부, 복구 성공과 시각)에 재전송 일정을 적용했다
(`mac_goodput.py`). 물리 계층의 재전송은 실행하지 않았다.

| 경우 | 일정 (슬롯 시작 T0 기준) |
|---|---|
| 기존 수신기가 복호 | T0 + 4.5 ms에 전달 |
| NRx가 복구 | T0 + 0.5 ms + NRx 종료 시각에 전달, 재전송 없음 |
| 복구 후보가 아니거나 NRx를 얻지 못함 | T0 + 7.5 ms의 UL 슬롯에 재전송 (기존 일정과 같음) |
| NRx를 돌렸으나 복구 실패 | T0 + 12.5 ms의 UL 슬롯에 재전송 (5 ms 늦음) |
| 재전송 | 성공 확률 0.95(soft combining), 실패하면 7.5 ms 뒤 다시, 최대 4회 |

- 사용자는 항상 보낼 데이터가 있다(full buffer). 재전송 하나는 새 데이터가 쓸 UL 슬롯 하나를 쓴다.
- goodput = 새 데이터를 전달한 슬롯 / 전체 슬롯. 지연 = 슬롯 시작에서 전달까지.

## 4. 비교 대상 보강: YinYangRAN 방식의 재구성

### 4.1 원문의 설계와 재구성

YinYangRAN(INFOCOM'24)의 pre-print를 읽고 설계를 옮겼다. 원문의 코드는 공개돼 있지 않다. 아래는 재구성이고, 결과는
"신뢰도 추정기로 비율을 고르는 방식"의 결과로 적는다.

| | YinYangRAN (원문) | 이 testbed의 재구성 |
|---|---|---|
| 결정 주기 | δ = 1초 이상 | 1초 (UL 슬롯 400개) |
| 상태 | 직전 결정 구간의 traffic 히스토그램 | 직전 1초의 "GPU별 활성 셀 비율" 히스토그램 (5칸) |
| 행동 | DU의 MPS 할당 (ML은 나머지) | AI의 MPS 비율: 10/20/30/50/70% (낮은 우선순위 AI는 30/50/70/100%) |
| 신뢰도 | 제때 처리한 TB의 비율 | 두 값: 복구 유지율(AI 없는 실행 대비), L1 마감을 지킨 TB의 비율 |
| 추정기 | 분위수 손실로 오프라인 학습한 NN, 최저 분위수가 목표를 넘어야 함 | MLP(은닉 16), 분위수(pinball) 손실, 분위수 0.1 / 0.25 / 0.5; 0.25 분위수가 목표를 넘어야 함 |
| 선택 | 조건을 만족하는 가장 작은 DU 할당 (YYR-Lite) | 조건을 만족하는 가장 큰 AI 비율 (같은 뜻) |
| 목표 | 신뢰도 1 − ε, 기본 ε = 0.1 | 복구 유지율 0.97, L1 0.999 |

  worker를 미리 띄워 두므로 모델을 다시 올리는 시간이 없다.
- 재구성하지 않은 것: YYR-Full의 look-ahead(재설정 비용을 고려해 여러 구간을 내다보는 선택).
- 학습 자료: 일정한 부하 4가지(활성 셀 비율 0.25 / 0.5 / 0.75 / 1.0) × 비율 5가지(낮은 우선순위는 4가지), 각 20초,
  시드 7(평가 시드 1–5와 다름). 결정 구간 하나가 표본 하나다. 코드 `yyr_train.py`, `controller5.py`(yyr 모드),

## 5. AI 범위 확장: 토큰 생성과 여러 모델

### 5.1 설계

v13까지의 AI 작업은 Qwen2.5-1.5B의 prefill(프롬프트 처리) 하나였다. v14는 다섯 종류를 한 GPU에서 함께 돌린다.

| 종류 | 모델 | 작업 | 시간 제한 |
|---|---|---|---|
| chat | Qwen2.5-1.5B | 프롬프트 처리 뒤 출력 토큰을 최대 64개 생성 | 첫 토큰 200 ms, 그 뒤 토큰마다 50 ms |
| large | Qwen2.5-3B | 프롬프트 처리 | 400 ms |
| embed | BAAI/bge-base-en-v1.5 (BERT) | 문장 임베딩, 배치 1/4/16 | 50 ms |
| vision | google/vit-base-patch16-224 | 이미지 분류, 배치 1/4/16 | 50 ms |
| filler | Qwen2.5-1.5B | 1024 token 프롬프트 처리, 항상 대기 중 | 없음 |

**모든 작업을 "단위"로 쪼갠다.** 단위는 고정 버퍼 위에서 잡은 CUDA graph 하나이고, 혼자 돌 때의 GPU 시간을 한 번
재서 한도(p99.9의 1.1배)로 쓴다(`bench_units5.py`, `results/backstop_slot/unit_bounds5.json`).

| 모델 | 단위 | 한도 (ms) |
|---|---|---|
| Qwen2.5-1.5B | layer 하나 × 128 / 512 / 1024 token | 0.37 / 0.84 / 1.33 |
| | 출력 토큰 하나 = 묶음 10개 (layer 3개씩) | 묶음당 0.59–0.72 |
| Qwen2.5-3B | layer 하나 × 128 / 512 / 1024 token | 0.51 / 1.14 / 1.87 |
| bge-base | layer 하나 × 배치 1 / 4 / 16 | 0.11 / 0.15 / 0.28 |
| ViT-base | layer 하나 × 배치 1 / 4 / 16 | 0.13 / 0.19 / 0.40 |

- 단위는 한도에 따라 크기 등급(0.45 ms 이하 / 1.2 ms 이하 / 그 위)에 속한다. controller의 허락 규칙은 등급만 본다.
  그래서 prefill용으로 만든 규칙(기존 수신기 옆 허용 크기, NRx 옆 lane 여유, 조각 중단)이 모든 종류에 그대로 적용된다.
- 출력 토큰 생성(decode)은 KV cache를 쓰는 1-token 단위다. 토큰 하나를 10개 묶음으로 나누어, 묶음 사이에서 무선
  작업에 GPU를 내줄 수 있게 했다. 세션(KV cache)은 GPU당 4–6개이고 가중치는 공유한다.
- worker(`ai_worker5.py`)는 조각 안에서 "마감이 가장 이른 작업의 다음 단위"를 고른다. filler는 다른 작업이 없을 때만
  돈다.
- 요청은 서버 전체에 하나의 도착 목록으로 오고(`ai_arrivals5.py`), controller(`controller6.py`)가 요청마다
  "가장 먼저 끝낼 GPU"에 배정한다. 제한 안에 끝내지 못할 요청은 받지 않는다(admission). chat은 세션이 빈 GPU에만
  배정한다. 기준선(고정 비율, 낮은 우선순위)도 같은 배정과 admission을 쓴다.

## 6. link adaptation과의 결합

### 6.1 방법

- 2-UE 셀(16QAM, 273 PRB, NVlabs link simulation의 상관 낮은 TDL 채널)의 MCS를 10–16(표 1, 부호율 0.33–0.64)으로 바꿨다.
- 고정 Es/No 4.5–7.5 dB(0.5 dB 간격)에서 슬롯을 생성하고, 두 수신기로 같은 슬롯을 복호했다(LDPC 20회, MCS와
  Es/No마다 슬롯 150개 = TB 300개). `nrx_large`는 16QAM의 LLR을 내므로 부호율이 달라도 같은 TensorRT 엔진을 쓴다.
- goodput = `TB 크기 / (1 + 오류율 / 0.95)`. 재전송 하나가 UL 슬롯 하나를 쓰고 0.95의 확률로 성공한다.
- 복구 경로의 오류율 = 기존 수신기 오류율 − 0.86 × (NRx만 성공한 비율). 0.86은 시간 조건을 적용한 시스템이 오프라인
  복구 가운데 지키는 비율이다(채널 혼합 조건: 실패의 38% 대 44%).
- MCS를 고르는 규칙: "goodput 최대"(goodput이 가장 큰 MCS), "10% 목표"(첫 전송 오류율이 10% 이하인 가장 높은 MCS).
- 실행 `la.sh DoubleTDLlow 5,6,7 150`, `la_more.sh`; 분석 `analyze_la.py`, `table_la.py`; 원본
  `results/backstop_slot/link_adaptation_DoubleTDLlow.json`, `raw/la_DoubleTDLlow_m*.json`.

### 6.3 읽는 법

- **질문: 복구 경로가 있으면 더 높은 MCS를 쓸 수 있는가. 답: 시험한 Es/No의 약 절반에서 한 단계.** 복구 경로는 오류율
  10% 지점을 0.4–0.5 dB 낮추고, MCS 한 단계의 간격은 0.84–1.14 dB다. 두 단계 오른 점은 없다.
- goodput 이득은 평균 +5.1–5.2%다. 10% 목표 규칙에서 MCS를 그대로 두면 +2.9%다. MCS를 올려서 더 얻는 것은 평균
  2.3%p이고, MCS가 오른 점에서는 +3.5–9.4%다.
- MCS가 오르면 첫 전송의 실패가 늘어 NRx 수요가 는다(5.0 dB: MCS 12 → 13이면 기존 수신기 실패 1.7% → 10.7%).
  NRx 수요가 늘면 AI가 쓸 GPU 시간이 준다(2.2절: 약한 셀 4개 37.6k, 8개 11.9k).
- **오류율 목표를 올리는 경우.** MCS를 "기존 수신기의 첫 전송 오류율이 목표 이하인 가장 높은 값"으로 고르고 목표를
  바꿨다(Es/No 7개의 평균, 슬롯당 bit).

  | 목표 | 기존 수신기만 | 복구 경로 (같은 MCS) | 이득 |
  |---|---|---|---|
  | 5% | 74.5k | 75.5k | +1.3% |
  | 10% | 76.1k | 78.4k | +2.9% |
  | 20% | 75.9k | 80.3k | +5.8% |
  | 30% | 73.8k | 80.3k | +8.8% |
  | 40% | 72.6k | 79.7k | +9.8% |

  기존 수신기만 쓰면 10% 목표가 최선이고(76.1k), 복구 경로가 있으면 20–30% 목표가 최선이다(80.3k, 최선끼리 +5.5%).
  질문 "목표 BLER을 올렸을 때 셀 처리량이 얼마나 오르는가"의 답이다.
- 한계: 고정 Es/No, 채널 한 종류, 점마다 TB 300개다. 오류율 10% 근처의 점(5.5 dB의 MCS 14: 10.2%, 6.5 dB의
  MCS 15: 10.8%)은 통계 오차 안에 있어, "MCS가 오른 점"은 7개 중 3개에서 5개 사이다. 채널이 변하는 조건의 rate
  control과 HARQ 결합은 실행하지 않았다.

## 9. 미래를 아는 스케줄과의 거리 (2026-10-04, GPU 실행 없음)

### 9.1 계산

| 값 | 정의 |
|---|---|
| 규칙의 이상값 | NRx가 도는 동안만 그 GPU의 AI를 끈다(중단 지연 0, 허락 손실 0). AI 시간 = 1 − ΣS / (N·H) |
| 미래를 아는 스케줄 | 시작 시각을 AI 없는 실행과 같게 둔다(잃는 후보 없음). NRx 옆의 AI는 그 NRx가 다음 실행의 시작 전에 끝나는 한도까지 돈다 |
| r | NRx 혼자 / AI 옆의 실행 시간 = 6.29 ms / 8.01 ms = 0.786 (전 부하, 낮은 우선순위만 쓴 실행에서 측정) |

| NRx 배정 | 늘인 실행이 가장 먼저 끝나는 NRx에 배정한다. 시작 시각이 고정이면 줄이는 시간의 합이 가장 작다(비용 max(0, f − s)가 볼록) |

## 10. 닫힌 루프 link adaptation (2026-10-04–05, job 59345188, 59362400)

6장은 MCS를 고정하고 잰 오류율의 계산이다. 이 장은 outer-loop link adaptation을 런타임에 넣고 2-UE 셀이 슬롯마다
MCS를 고르게 한 측정이다. 실험 전의 예상은 "복구를 6–10% 잃으면 MCS가 한 단계 내려가 goodput이 약 10% 준다"였고,
측정은 이 예상과 다르다. 전체 표와 그림은 README 6.13절에 있다.

### 10.1 구현과 방법

| 항목 | 내용 |
|---|---|
| 셀 worker (`conv_worker.py`) | 2-UE 셀이 MCS 10–16의 슬롯 ring을 단계마다 하나씩 갖는다. 단계 위의 포인터를 TB마다 갱신한다: 재전송이 필요한 TB는 −δ, 그렇지 않은 TB는 +δ·τ/(1−τ) (δ = 0.25단계, τ = 목표). 슬롯의 MCS는 포인터의 정수 부분. 결과는 6 UL 주기(15 ms) 뒤에 반영 |
| 재전송이 필요한 TB | 기존 수신기가 복호하지 못했고 NRx가 복구 마감(11.5 ms) 전에 복구하지도 못한 TB. NRx의 UE별 CRC 결과를 공유 상태(`C_NRX_MASK`)로 받는다 |
| NRx lane (`nrx_lane.py`, `mu_radio.py`) | 슬롯의 단계(`C_LEVEL`)를 읽어 그 단계의 rate recovery와 LDPC 설정으로 전환한다. NRx 엔진은 하나다 |
| 설정 (`make_config.py --la`) | `MCS,...:목표[:δ[:지연[:시작 단계]]]` |
| 채널 | 상관 높은 채널, Es/No 16 dB. 단계마다 슬롯 768개 생성(`la_cl_gen.sh`), 셀은 512개를 반복 |
| goodput | (TB 비트의 합) / (TB 수 + 재전송 수 / 0.95). 20초 실행에서 앞의 2초 제외 (`analyze_la_closed.py`) |
| 실행 | `la_cl.sh`, `la_cl2.sh`, `la_cl_chain.sh`–`la_cl_chain4.sh`, `la_cl_chain6.sh`. 실행 179개, 실패 없음 |

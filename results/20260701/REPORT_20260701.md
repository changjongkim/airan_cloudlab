## 4. 발견 (오늘 데이터만)

### Finding 1 — L1이 cudaFree의 비대칭 victim

![Figure 1](figures/fig1_asymmetric_victim.png)

| 조건 | L1 cudaFree calls | AI cudaFree calls | 비율 |
|---|---|---|---|
| X3 NeuralRx coloc | **2,463** | **3** | 821:1 |
| X2 NeuralRx cross-part | 2,516 | 2,303 | 1.1:1 |
| X5 chanpred cross-part | 2,516 | 0 | ∞ |
| X6 chanpred coloc | 2,516 | 0 | ∞ |

**핵심**:
- L1 (cuPHY)는 30 s capture window에서 **2,400 회 이상 cudaFree 호출** (frame당 1회 패턴)
- chanpred AI는 **0회**, NeuralRx coloc은 **3회**
- → **cudaFree blocking의 진짜 caller는 L1**. AI는 거의 호출 안 함.

---

### Finding 2 — cudaFree는 bimodal distribution을 가짐

![Figure 2](figures/fig2_bimodal_distribution.png)

cudaFree per-call duration이 **fast (<100 µs)** 와 **slow (>1 ms)** 두 mode로 갈림:

| 조건 | fast (<100 µs) | mid (100 µs–1 ms) | slow (>1 ms) | slow 비중 |
|---|---|---|---|---|
| X2 NeuralRx cross-part | 1,238 | 1,219 | 6 | **0.2%** |
| **X3 NeuralRx coloc** | **65** | **127** | **2,271** | **92%** |
| X5 chanpred cross-part | 1,233 | 1,229 | 1 | 0.04% |
| **X6 chanpred coloc** | 60 | 800 | **1,603** | **65%** |

**핵심**:
- Cross-partition에서는 cudaFree의 거의 모두가 fast/mid mode (slow는 0.04~0.2%)
- Same-partition coloc에서는 slow mode가 65~92%로 폭발
- → placement 변경 하나만으로 cudaFree의 mode 분포가 결정됨

---

### Finding 3 — Cross-process implicit sync 직접 증명 ⭐

![Figure 3](figures/fig3_cross_process_sync_proof.png)

**X3 NeuralRx coloc** (왼쪽 그림):
- 매 L1 cudaFree에 대해, 그 시점에 AI process에서 실행 중인 kernel의 overlap 시간 측정
- N=2,271 (slow mode만)
- **r² = 0.939** — cudaFree duration 변동의 94%가 AI kernel overlap으로 설명됨
- **slope = 0.96** — AI kernel이 1 µs 길어지면 cudaFree도 1 µs 길어짐 (거의 1:1)
- 즉 **L1 cudaFree 대기 시간 = 그 순간 AI kernel이 남은 실행 시간**

**X2 NeuralRx cross-partition** (오른쪽 control):
- AI는 다른 MIG instance에 있음
- L1 cudaFree와 AI kernel 사이 correlation 없음
- → cross-process sync는 **같은 MIG partition 안에서만 작동**

**결론** (가설 아니라 fact):
> *L1 cudaFree blocks until the current AI kernel on the same MIG partition completes.  
>  Pearson r² = 0.94, N = 2,271, slope ≈ 1.0.*

### Finding 4 — Mitigation challenge: Sync wait conservation 🚨

![Figure 4](figures/fig4_sync_conservation.png)

PROOF 6: cudaFree를 LD_PRELOAD shim으로 가로채서 no-op으로 만들었음 (실제로 free 안 함).

| API | Baseline (p5) | Skip cudaFree (p6) | 변화 |
|---|---|---|---|
| cudaFree | 9,232 ms | **0 ms** | 완전 제거 ✓ |
| cudaMemcpyAsync | 3,746 ms | **12,788 ms** | **+9,042 ms (3.4×)** 🚨 |
| cudaMalloc | 106 ms | 193 ms | +87 ms |
| cudaStreamSync | 58 ms | 60 ms | 동일 |
| **Total host time** | **13,084 ms** | **12,981 ms** | **0.8% 차이 (essentially same)** |

**해석**: cudaFree에서 9 초를 줄였더니 cudaMemcpyAsync에서 정확히 9 초가 늘어남.
- GPU work queue를 drain하는 implicit sync는 **어딘가에서 일어나야 함**
- cudaFree를 skip하면 다음 host-blocking API (cudaMemcpyAsync)가 그 짐을 그대로 떠안음
- **Total host sync wait time이 conserved**

**Paper에 미치는 함의**:
- "memory pool로 cudaFree 제거하면 해결" 이라는 단순 mitigation은 **작동하지 않음**
- 효과적 mitigation 후보:
  1. GPU work queue 자체를 줄이기 (per-frame allocation 제거 + buffer reuse)
  2. `cudaMallocAsync` + `cudaFreeAsync` (stream-ordered, queueing)
  3. CUDA Graph capture (frame을 graph로 한 번에 dispatch)
  4. cuPHY 자체 rearchitect (memory pool 도입)

→ 이건 우리 deck/paper의 **mitigation 권고 수준을 한 단계 끌어올림**.

### Finding 5 — chanpred는 cudaFree 자체를 안 부름 (production 패턴)

![Figure 5](figures/fig5_chanpred_no_cudafree.png)

| 워크로드 | cudaLaunchKernel | cudaMalloc | cudaFree | L1 영향 |
|---|---|---|---|---|
| chanpred (X4 alone) | **3,428,796** | 0 | **0** | zero (16× kernel launch에도 무영향) |
| NeuralRx (X1 alone) | 5,547 | 193 | 903 | triggers L1 cudaFree blocking |

**해석**:
- chanpred는 **pre-allocated buffer pool + event/stream 기반 처리**
  → 매 frame allocate/free 없음, kernel launch 수백만 번 + cudaFree 0회
- NeuralRx는 매 inference 마다 allocate/free 패턴 → AI 자체도 cudaFree 호출
- **paper의 가장 강한 한 줄**:
  > "chanpred: 3.4 M kernel/sec + 0 cudaFree → L1 무영향  
  >  NeuralRx: 9 K kernel/sec + 900 cudaFree → L1 catastrophic"  
  > **kernel launch rate가 아니라 memory allocation pattern이 AI-RAN feasibility를 결정**.

> *"The Unreachable Slack: How Cross-Process cudaFree Sync Blocks AI-RAN at 1:1 Ratio with Concurrent AI Kernels

### Finding 9 — 2g 작은 partition은 별개 패턴 (SM contention 영향)

![Figure 9](figures/fig9_2g_anomaly.png)

2g (가장 작은 MIG instance)에서는 cross-part workload 추가에 따라 **cudaFree 시간이 변동함**:

|---|---|---|
| chanpred coloc | 5881 | 67% |
| + HBM (2g sidecar) | 7243 | 74% |
| + chanpred (2g sidecar) | 4574 | 53% |
| + ResNet (2g sidecar) | 3029 | 45% |

- 4g/3g/7g 와 달리 2g에서는 cross-part workload 추가시 cudaFree가 **줄어듦**

→ **paper narrative**: realistic deployment의 3g/4g partition 에서는 cudaFree contention이 dominant. 너무 작은 2g에서는 AI 자체가 불가능해서 contention 발생할 일이 적음.

## 15. Chain 8 — Async Mitigation Shim 검증 ⭐⭐⭐

### 15.1 목적
Finding 3 (cudaFree = implicit sync)의 theoretical fix 테스트:
- **Option A**: `cudaFree()` → `cudaFreeAsync()` LD_PRELOAD shim
- **Option B**: `cudaMalloc()` + `cudaFree()` → `cudaMallocFromPoolAsync()` + `cudaFreeAsync()` (완전 async pool)

### 15.2 Chain 8 설계 (16 conditions)
```
per cells ∈ {4, 10, 40, 60} on 3g partition:
  A_c{N}_alone            baseline (no coloc, no shim)
  A_c{N}_nrx_baseline     NRx coloc, no shim (Chain 7 X3 재현)
  A_c{N}_nrx_freeasync    NRx coloc + Option A
  A_c{N}_nrx_pool         NRx coloc + Option B
```

### 15.3 Dry-run 검증
Both shims intercept correctly:
- Option A: 339 cudaFree calls → cudaFreeAsync (0 fallback)
- Option B: 339 malloc + 339 free 모두 pool 통과 (0 fallback)

### 15.4 결과 — Total host CUDA time (ms)

| variant | c=4 | c=10 | c=40 | c=60 |
|---|---|---|---|---|
| **Baseline** (no coloc) | 170 | 392 | 1680 | 2529 |
| **NRx coloc** (no shim) | 2537 | 6372 | 25348 | 25915 |
| **Option A** (cudaFreeAsync) | 2408 | 6363 | **25570** | 25955 |
| **Option B** (cudaMemPool) | 2523 | 6389 | **25649** | 26016 |

**Coloc penalty (baseline vs coloc): +2367ms → +23670ms** (cells 4→40)
**Option A/B 감소량**: ~0% (거의 완전 동일)

### Finding 15 — Async Mitigation Fails ⭐

![Figure 16](figures/fig16_chain8_sync_conservation.png)

Chain 8 cells=40 상세 breakdown:

| API | Baseline coloc | Option A | Option B |
|---|---|---|---|
| cudaFree | **18076 ms** | 0 | 0 |
| cudaFreeAsync | 0 | **15 ms** | **11 ms** |
| cudaMallocFromPoolAsync | 0 | 0 | 36 ms |
| cudaMemcpyAsync | 7034 ms | **25221 ms** | **25539 ms** |
| cudaMalloc | 235 ms | 161 ms | 0.6 ms |
| **Total** | **25348 ms** | **25570 ms** | **25649 ms** |

**핵심**:
- cudaFree 18076ms → cudaMemcpyAsync +18186ms (Option A) / +18505ms (Option B)
- **100% conservation** — sync wait은 반드시 어딘가에서 발생

### Finding 16 — Sync wait은 cudaMemcpyAsync 로 결정론적 이동

![Figure 17](figures/fig17_chain8_mitigation_across_cells.png)

모든 cell 크기에서 동일 패턴:
- cells=4: 코로c penalty 100% 유지 (baseline vs shim 변화 <1%)
- cells=10: 100% 유지
- cells=40: 100% 유지  
- cells=60: 100% 유지

→ Async API는 **문제 위치를 옮길 뿐, 총 대기 시간을 줄이지 않음**

### 15.5 Paper 함의

**결정적 명제**:
> *"Stream-ordered async CUDA APIs (cudaFreeAsync, cudaMallocFromPoolAsync) do NOT reduce host synchronization overhead in coloc scenarios. Sync wait is deterministically conserved and shifts to cudaMemcpyAsync."*

**진짜 mitigation의 조건**:
1. **GPU work queue 자체 축소** — cuPHY의 per-frame allocation 제거
2. **CUDA Graph capture** — frame을 통째로 pre-compile, 단일 launch
3. **cuPHY 내부 rearchitect** — chanpred 스타일 persistent buffer pool
4. **하드웨어 격리** — MIG를 진짜 별도 물리 그래프로 분리

**Paper narrative 최종**:
> **"The Unreachable Slack: Sync Wait Conservation Defeats Async API Fixes in AI-RAN cuPHY  
>  — Why Even cudaFreeAsync Cannot Rescue Colocated Workloads"**

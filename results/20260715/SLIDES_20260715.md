## Slide 1 — 한 줄 결론

> **cuPHY L1과 AI 워크로드를 같은 GPU에 놓을 때 발생하는 cudaFree sync는
> API 레벨에서 절대 못 고친다. Spatial multiplex(MPS/MIG) 또는 launch 개수 자체를
> 극한으로 줄이는 것(megakernel), 이 둘 만이 유일한 escape path다.**

### 왜 이게 중요한가

- AI-RAN 배포 = cuPHY (5G L1) + AI (Neural RX / Beamforming) 동거
- TS mode + coloc = **27.5s의 host CUDA 시간**이 sync에 갇힘 → L1 real-time budget 파괴
- 이 sync를 어디서 어떻게 없앨 수 있는지가 AI-RAN 시스템 설계의 핵심 질문
- **7개 chain (3주치) 실험이 이 결론에 수렴함** — 오늘의 Chain 12가 real cuPHY에서 재확인

### 세 개의 계층에서 접근했음

| 계층 | 방법 | 결과 |
|---|---|---|
| **CUDA API** | 5가지 LD_PRELOAD shim (Chain 9) | ❌ 실패 확정 |
| **Execution model** | MPS spatial multiplex | ✅ Sync 사라짐 |
| **Architecture** | Megakernel (launch → 1개) | ✅ Sync 사라짐 (단, 흉내) |

## Slide 2 — 세 계층별 실험 결과 (Top-level)

### ① API 레벨 — **실패 확정**

Chain 9에서 5가지 shim 테스트, Chain 12에서 real cuPHY로 재현:

```
baseL1 (real cuPHY)          cudaFree 18,513 ms  memcpy  7,374 ms  →  27,458 ms
baseL1 + arena_shim          cudaFree      0 ms  memcpy 26,082 ms  →  27,557 ms
                                          ↑                ↑              ↑
                                   완전 제거        이만큼 증가      총합 그대로
```

**Conservation law**: sync는 어떤 API를 후킹하든 다음 host-blocking call로 이동만 함.
cudaFree를 없애면 memcpyAsync가 대신 sync를 흡수. 총 host time은 27.5s로 불변.

### ② Execution model 레벨 — **MPS로 해결됨**

```
baseL1 (TS mode)     alone: 2,905 ms    +NRx: 27,458 ms   ← 9.4× 폭발
baseL1 (MPS100)      alone: 3,151 ms    +NRx:  3,133 ms   ← 폭발 안 함
```

MPS는 GPU를 시간이 아니라 **공간(SM)** 으로 나눔 → 두 프로세스 큐를 reconcile할
필요 없음 → sync trigger 자체가 사라짐. **소프트웨어 변경 없이 배포 가능한 유일한 handle.**

### ③ Architecture 레벨 — **megakernel로 해결됨 (단, synth)**

```
baseL1 (real cuPHY,   39,140 launches)  +NRx: 27,458 ms
multiBase (synth 6-stage, 10,100 launches) +NRx:  2,271 ms
multiMega (Approach B, 6 launches)          +NRx:     39 ms   ← 703× 개선
```

Launch를 6개로 줄이면 sync trigger 지점 자체가 없어짐.
**단 이 결과는 synth workload — real cuPHY rewrite는 미검증 (Slide 4 참조).**

## Slide 3 — 근거 데이터 (Chain 12, TS + NRx coloc)

### 5개 workload 비교 (3-trial 평균)

| Workload | 무엇 | Launches | cudaFree | memcpy | **Total** |
|---|---|---:|---:|---:|---:|
| `baseL1` | 진짜 pyaerial 컴포넌트 (ChEst, MMSE, LDPC) | 39,140 | 18,513 ms | 7,374 ms | **27,458 ms** |
| `baseL1_arena` | 위 + LD_PRELOAD 버퍼풀 shim | 39,364 | **0** | 26,082 ms | **27,557 ms** |
| `multiBase` | Synth 6-stage per-iter alloc/launch/free | 10,100 | 626 ms | 0 | 2,271 ms |
| `multiMega` | 같은 6-stage → 1 launch megakernel | **6** | 0 | 0 | **39 ms** |
| `persistMega` | Elementwise persistent kernel | 2 | 0 | 0 | 41 ms |

### 두 개의 대비 축이 이 표에서 동시에 보임

**Baseline vs Arena 대비 (같은 39K launches, 다른 API 사용)**:
27,458 → 27,557 ms — sync가 이동만 함, 총합 불변  
→ **API 우회는 불가능**

**Baseline vs Megakernel 대비 (다른 launch 개수)**:
27,458 → 39 ms (703×)  
→ **launch를 줄이면 sync 사라짐**

### 왜 launch가 변수인지 — log-log 상관관계 (`fig12`)

Launch가 4자릿수 걸쳐 변할 때 total host time이 거의 직선으로 따라옴.
매 launch가 "sync가 trigger될 수 있는 확률 지점" → launch 개수가 페널티의 근본 변수.

### 참고: MPS100 조건에서는 launch가 39K여도 sync 안 걸림

```
baseL1_MPS100_nrx:      launches 57,616  →  Total 3,133 ms
baseL1_TS_nrx:          launches 39,140  →  Total 27,458 ms   ← 9× 차이
```

**같은 launch 개수라도 execution model(TS vs MPS)에 따라 sync 유무가 결정됨.**
Sync는 launch 개수만의 함수가 아니라 **"temporal multiplex에서 매 launch가 trigger될 수 있다"**는
조건부 명제. MPS로 그 조건 자체를 없애면 launch가 많아도 안 걸림.

## Slide 4 — 한계 & 다음 세션

### 정직하게 밝혀야 할 것

**multiMega의 39 ms는 real cuPHY 숫자가 아님.**

| Stage | Real cuPHY | multiMega |
|---|---|---|
| Channel Estimation | LS/MMSE + TensorRT AI-ChEst | memcpy + arithmetic |
| MMSE Equalization | 4×4 행렬 역행렬 per PRG | GEMM-like op만 |
| LDPC Decode | min-sum iterations, irregular access | XOR loop |
| CRC | CRC-24A/B/16 polynomial | accumulator |
| SM 활용 | Tensor Core WMMA, shared mem tiling | grid-stride loop |

즉 megakernel은 **HBM 대역폭 특성만 real cuPHY와 유사한 proxy**.

### 증명한 것 vs 못한 것

- ✅ **구조적 명제**: "Multi-stage HBM-bound workload를 1 launch로 묶으면 sync 사라짐" — 확정
- ⚠️ **실증적 명제**: "진짜 cuPHY PUSCH RX를 megakernel로 rewrite했을 때 몇 ms?" — 미검증
- ✅ **부정 명제**: "API-layer fix는 real cuPHY에서도 안 됨" — Approach C가 확정

### Approach A (`PuschRxPipelineFactory`) — 이번엔 놓친 것

- 시도했으나 `cuphyCreatePuschRx()` 내부에서 SIGSEGV
- gdb + cuBB_system_checks로 원인 확정: **driver 550 vs 요구 570.104 ABI mismatch**
- Reversible 조치(persistence/clocks/hugepages) 모두 적용해도 crash 유지
- **다음 세션에서 driver 570 업그레이드 + reboot 후 재실행 예정**

### 다음 세션 우선순위

1. **Driver 570 업그레이드 + reboot** → Approach A 재실험, MIG 실험 unblock
2. **MIG cross-partition vs same-partition** — spatial 우회의 두 번째 mechanism 검증
3. **MPS 30% × HBM stress** — SM 캡핑이 HBM 대역폭 경쟁을 못 막는다는 가설
4. **(장기) cuPHY C++ source 개조** — 진짜 megakernel PUSCH RX 만들기, 2~4주 규모

### 논문/보고 스토리라인 (제안)

> "We show that in temporal-multiplex GPU sharing, cross-process CUDA sync
> penalty is a conserved quantity — API-layer buffer pool mitigations relocate
> it but never eliminate it. Only two independent escape paths exist:
> spatial multiplex (MPS/MIG) at the execution-model layer, or launch-count
> collapse (megakernel) at the architectural layer. We verify the API-layer
> failure directly on real cuPHY components; the megakernel benefit is
> demonstrated on a cuPHY-structured synthetic workload and its transfer
> to a full cuPHY rewrite remains an open engineering question."

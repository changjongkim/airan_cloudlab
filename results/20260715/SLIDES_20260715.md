## Slide 1 — MPS는 **execution model 레벨에서** sync를 우회할 수 있다 (20260708 Round 3)

![fig2_round3_fair_comparison](../20260708/figures/fig2_round3_fair_comparison.png)

**동일 42 SM (MIG 4g)에서 execution mode만 바꾼 fair comparison** (mechanism vs resource decomposition):

| Condition | Execution | 42 SM 공유 | cudaFree | vs baseline |
|---|---|---|---:|---:|
| MIG 4g alone, no MPS | temporal (1 ctx) | 없음 | 1,764 ms | 1.00× |
| **MIG 4g + NRx, no MPS** | **temporal (2 ctx)** | 공유 | **18,599 ms** | **10.55×** |
| MIG 4g alone, MPS on | spatial | 없음 | 1,889 ms | 1.07× |
| **MIG 4g + NRx, MPS on** | **spatial** | 공유 | **1,794 ms** | **1.02×** |

**해석**:
- 자원(42 SM)을 고정한 채 execution mode만 temporal → spatial로 바꿨을 뿐인데
  10.55× 페널티가 1.02×로 소멸.
- 즉 MPS의 이득은 **"자원 많아서"가 아니라 "spatial multiplex mechanism 그 자체"** 때문.
- Sync는 API가 아니라 **temporal-multiplex라는 execution model의 속성**이라는 걸
  기계적으로 증명함.

**이 slide만 보면 "MPS 짱"으로 오해할 수 있으나 다음 slide가 뒤집는다.**

## Slide 2 — MPS는 실전 배포 도구가 아니다: HBM stress 한 방에 무너짐 (20260708 §4)

![fig3_percall_distribution](../20260708/figures/fig3_percall_distribution.png)

같은 20260708 세션에서 co-tenant AI 워크로드를 **HBM 대역폭 포화형**으로 바꿔서 재측정.
Per-call `cudaFree` 지연 분포를 세 개의 signature로 분해:

| Condition | Fast <1ms | Slow 1-10ms | **Cat >10ms** | p50 | Mechanism |
|---|---:|---:|---:|---:|---|
| TS alone | 100% | 0 | 0 | 177 µs | sync 없음 |
| TS + NRx | 5% | 95% | 0 | 4,725 µs | **temporal sync** |
| MPS + NRx | 100% | 0 | 0 | 167 µs | spatial 우회 성공 |
| **MPS + HBM stress** | **2%** | 0 | **98%** | **58,336 µs** | **HBM 대역폭 starvation** |

**cudaFree 총량**:
| Condition | cudaFree total | L1 iters 완료 |
|---|---:|---:|
| MPS + NRx (compute-bound AI) | 1,685 ms | 7,263 |
| **MPS + HBM stress** | **22,645 ms** ← temporal보다 나쁨 | **372** (alone의 5%) |

**해석**:
- MPS는 SM은 공간 분할하지만 **HBM 대역폭은 물리적으로 공유** → co-tenant가
  HBM을 saturate하면 L1 자기 커널이 HBM read에서 stall → cudaFree가 그걸 기다림 → 폭발.
- 위 표에서 MPS + HBM stress의 `cudaFree` = 22,645 ms는 **temporal + NRx의 18,599 ms보다도 큼**.
- **MPS의 이득은 workload-conditional**이며, 실제 배포에서는 co-tenant AI가
  memory-bound인지 compute-bound인지 사전에 알 수 없음 → SLA 보장 불가.
- 결론: **MPS는 "우연히 compute-bound인 AI가 co-tenant일 때만 통하는" 조건부 solution**.
  AI-RAN 배포 default 아님.

**MIG cross-instance가 진짜 답이다** — 자원(SM + HBM slice + L2 bank + memory controller)이
물리적으로 분리되므로 co-tenant 특성과 무관하게 SLA 보장 가능.
(하지만 MIG는 이번 시리즈에서 same-partition만 검증 완료, cross-partition은 다음 세션 재실험 대기.)

## Slide 3 — API 레벨 우회는 5개 shim 모두 실패 (20260715 Chain 9)

![fig1_chain9_shims](figures/fig1_chain9_shims.png)

MPS가 조건부라면 **API 레벨에서 cudaFree만 fix하면 될까?** 5가지 LD_PRELOAD shim으로 시도.

| Shim | 무엇을 함 | cudaFree | memcpyAsync | **Total host** |
|---|---|---:|---:|---:|
| baseline (no shim) | 원본 | 18,578 ms | 7,355 ms | **27,472 ms** |
| cudaFreeAsync | free → async-stream free | 0 | 25,695 ms | 27,470 ms |
| cudaMemPool | malloc/free를 pool로 route | 0 | 26,050 ms | 27,525 ms |
| defer | free를 exit까지 지연 | 0 | 25,586 ms | 27,420 ms |
| **arena** | malloc = 캐시된 버퍼 재사용, free = slot 반환 | 0 | 26,100 ms | **27,556 ms** |

**Conservation law 발견**: shim이 cudaFree를 제거하면 정확히 그만큼 memcpyAsync가
부풀어서 **총 host 시간은 27.4~27.6 s로 일정**. 어떤 API를 어떻게 후킹하든 동일.

Sync는 특정 API의 속성이 아니라 **"temporal multiplex 하에서 다음 host-blocking API로
전이되는 conserved quantity"**임을 확인.

## Slide 4 — 이 실패가 real cuPHY에서도 그대로 재현됨 (20260715 Chain 12 Approach C)

![fig11_baseL1_vs_arena](figures/fig11_baseL1_vs_arena.png)

Slide 3의 arena shim을 이번엔 **synth workload가 아니라 real pyaerial + real cuPHY 컴포넌트**
(ChannelEstimator, MMSE Equalizer, LDPC Decoder) 위에 그대로 얹음.

| Condition | cudaFree | memcpyAsync | **Total host** | 관찰 |
|---|---:|---:|---:|---|
| baseL1 TS alone | 1,585 ms | 147 ms | 2,905 ms | compute floor |
| **baseL1 TS + NRx** | **18,513 ms** | 7,374 ms | **27,458 ms** | sync 발생 (89%가 sync) |
| **baseL1 + arena** TS + NRx | **0** | **26,082 ms** | **27,557 ms** | sync 이동만, 총합 동일 |
| baseL1 MPS100 + NRx | 1,714 ms | 156 ms | 3,133 ms | (compute-bound AI에서만) MPS 통함 |

**결정적 관찰**:
- arena shim이 real cuPHY의 cudaFree를 완전히 0으로 만듦 (18,513 → 0)
- 정확히 그만큼 memcpyAsync가 부풂 (7,374 → 26,082, 차이 +18,708 ms)
- **conservation law가 real cuPHY 환경에서 재현됨** — Chain 9는 synth의 우연이 아니라 원리적 결과

→ **결론**: real 배포 환경에서 "cudaFree 훅"으로 sync를 우회하려는 시도는
불가능임이 실증적으로 확정.

## Slide 5 — 관찰된 유일한 변수는 launch 개수 (Chain 12 log-log)

![fig12_launches_vs_host_time](figures/fig12_launches_vs_host_time.png)

Chain 12의 5개 workload를 launch 개수 vs total host time으로 log-log plot.
원 = alone, 삼각형 = +NRx coloc.

| Workload | Launches | TS + NRx total | 종류 |
|---|---:|---:|---|
| baseL1 (real cuPHY) | 39,140 | 27,458 ms | ✅ 진짜 pyaerial 컴포넌트 |
| baseL1_arena (real cuPHY + shim) | 39,364 | 27,557 ms | ✅ 진짜 pyaerial 컴포넌트 |
| multiBase (synth 6-stage per-iter) | 10,100 | 2,271 ms | ⚠️ synth 흉내 |
| multiMega (synth 6-stage megakernel) | 6 | 39 ms | ⚠️ synth 흉내 |
| persistMega (synth elementwise) | 2 | 41 ms | ⚠️ synth 흉내 |

**두 개의 축에서 읽어야 함**:
- **같은 launch 개수, 다른 API** (baseL1 ↔ baseL1_arena, real cuPHY): 27,458 → 27,557 —
  거의 동일. **API 바꿔도 launch 그대로면 sync도 그대로.**
- **다른 launch 개수** (baseL1 → multiMega): 39,140 → 6 launches. 하지만 **multiMega는 synth**.

**중요한 정직성**: multiMega/persistMega의 39 ms, 41 ms는 **synth workload 숫자**.
Real cuPHY로 rewrite한 결과가 아님.

**empirical 관계**: TS+NRx 조건에서 launch 개수 N일 때 total host time ≈ f(N) — log-log 산점도가
직선에 가까움. 이 관계가 어디까지 확장되는지가 Slide 6의 질문.

## Slide 6 — Megakernel이 real cuPHY에서 통할 근거 (정직한 평가)

![fig13_escape_paths](figures/fig13_escape_paths.png)

### Real cuPHY의 sync overhead를 정직하게 뜯어보면

baseL1 (real cuPHY) 숫자에서:
- **alone**: 2,905 ms — 순수 compute 시간
- **+ NRx**: 27,458 ms — 관측 총 시간
- **차이 24,553 ms (89%)는 sync overhead**, compute 아님

즉 real cuPHY의 27s는 **10%만 실제 계산이고 90%는 대기**. Sync만 제거해도 이론상 27s → 3s로 **최대 ~10× 개선 가능**.
(synth의 703×는 sync + compute 둘 다 없앴기 때문 — real cuPHY에서 그건 불가능.)

### Megakernel이 real cuPHY에서 통할 것으로 예상되는 근거 (empirical + 이론)

| 근거 | 강도 |
|---|---|
| ① Chain 12 log-log 상관: launch N개일 때 sync ≈ f(N) — real cuPHY 두 점(baseL1, baseL1_arena)이 이 관계에 들어맞음 | 강 |
| ② 89% of 27s = sync, 10%만 compute — sync만 제거해도 3s에 도달할 상한 존재 | 강 |
| ③ CUDA Graph pattern: 39K launch를 host-side 1 launch로 record/replay — NVIDIA-supported | 중 |
| ④ NVIDIA Aerial RT 로드맵이 persistent kernel 방향 (공개 자료) | 중 |
| ⑤ 우리 synth (multiMega)가 real cuPHY와 유사한 HBM-bandwidth-bound 특성에서 launch collapse 효과 재현 | 약 (synth) |

### Megakernel이 real cuPHY에서 통하지 **않을** 수 있는 이유 (미검증 리스크)

| 리스크 | 이유 |
|---|---|
| TensorRT AI-ChEst | 별도 `.engine` 파일, device 코드에 inline 불가 |
| LDPC decoder | 동적 iteration 수 (min-sum 수렴), cooperative groups로 해결 가능하나 비자명 |
| cuBLAS/cuFFT | host-launched library — 기존 fusion 어려움 |
| Register/shared memory pressure | 6 stage fuse 시 spilling → HBM traffic 증가 → 오히려 손해 가능 |
| pyaerial Approach A segfault | Chain 12에서 driver 570 요구로 못 돌림 — 진짜 batch API 성능 미확인 |

### 현실적 로드맵 (제안)

1. **Partial fusion** — LDPC와 ChEst를 각자 두고 MMSE+Equalizer 정도만 fuse. 39K → 예상 ~13K launches. 이론상 3× 개선.
2. **CUDA Graph capture** — 안정 서브셋을 그래프로 record. pyaerial의 D2H transfer가 방해했으나 cuPHY C++ patch로 해결 가능.
3. **Persistent kernel + 최소 CPU launcher** — Aerial RT 스타일. cuPHY 2.0급 규모.

### 결론 (한 문장)

> **Megakernel이 real cuPHY에서 통할 empirical 근거**는 "89%가 sync고 launch가 sync 유일 변수"라는 두 사실뿐이다.
> **이것만으로 10× 개선의 상한은 존재**하지만, TRT/LDPC/library 제약을 넘어 그 상한에 실제로 도달할 수 있는지는
> **cuPHY C++ source를 뜯어봐야 확인 가능**. 지금은 **가설**이지 검증된 결과 아님.

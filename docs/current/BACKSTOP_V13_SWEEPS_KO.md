기준일: 2026-10-02. 실행 job 59192512, 59199237(둘 다 nid200268, A100 80GB 4장). 숫자는 모두
`results/backstop_slot/sweep_*_j59192512_59199237.json`과 `v13_report_j59192512_59199237.md`에서 나온 값이다.
실행 방법은 10장.

> **2026-10-04:** 이 문서의 Antiphase는 v13 규칙(AI 조각이 멈추지 못함, lane 여유 3, 세 단위 크기를 모두 기존 수신기
> 옆에서 허용)이고 측정은 128 슬롯 반복이다. v14에서 규칙을 바꾸고 512 슬롯 반복·시드 5로 다시 쟀다

## 0. 요약

**무엇을 했나.** Antiphase와 기존 GPU 공유 방식 다섯 가지(고정 비율, 부하 따라 비율, 낮은 우선순위, 낮은
우선순위 + 부하 따라 비율, 유휴 시간만)를 같은 무선·같은 AI 요청으로 돌려 다섯 축을 sweep했다: AI 부하,
부하 변화(교대·무작위 계단·버스트), NRx 수요, 셀 수, GPU 수. 두 job에서 실행 522개(탐색·보정 65개 포함).

**실험 중에 바뀐 것.** 낮은 MPS 우선순위를 기준선에 넣으니 v7–v12의 Antiphase가 그 곡선 위에 있었다. 잃는
복구의 원인이 "빈 NRx가 없음"이라는 것을 확인하고 규칙을 고쳤다(2장): AI를 낮은 우선순위로 두고, NRx 옆에서는
다른 NRx가 돌고 있지 않을 때만 AI를 허락한다.

## 1. 무엇을 비교하는가

모든 실행의 공통 조건: 100 MHz 셀, TDD DDDSU(UL 주기 2.5 ms), L1 마감 4.0 ms, 복구 마감 11.5 ms, 두 수신기 모두
LDPC 20회, NRx는 NVlabs `nrx_large`, 약한 셀은 2-UE MU-MIMO(채널 섞임: 상관 낮음·높음·UMi), 실패 code block 9개
이하인 TB만 NRx로 보냄, GPU마다 NRx lane 1개, AI는 Qwen2.5-1.5B prefill 요청(시간 제한 200 ms)이고 dispatcher
하나가 GPU에 나눠 준다. NRx 규칙과 AI 요청, 입장 제어는 모든 방식이 같다. 다른 것은 **AI가 GPU를 언제 얼마나
쓰는가**뿐이다.

| 방식 | 하는 일 | 대응하는 기존 연구 | 실행 이름 |
|---|---|---|---|
| 고정 비율 | AI에 MPS 비율 P%를 고정으로 준다 | SoftBank·NVIDIA AI-RAN(MIG 40/60 분할) | `sP` |
| 부하 따라 바꾸는 비율 | 무선 부하가 높으면 낮은 비율, 낮으면 높은 비율. 전환 비용 0, 부하를 바로 알거나 1초 늦게 앎 | YinYangRAN (INFOCOM'24) | `dAxBlN` |
| 낮은 우선순위 | AI를 MPS 낮은 우선순위로 둔다. 비율 한도 없음(P100) 또는 P% 한도와 함께 | SMEC (NSDI'26)이 MEC 서버에서 쓴 MPS priority | `pP` |
| 낮은 우선순위 + 부하 따라 바꾸는 비율 | 위 둘을 합친 것. 기존 수단으로 만들 수 있는 가장 강한 비교 대상 | 해당 연구 없음(우리가 구성) | `eAxBlN` |
| 유휴 시간만 | GPU에 무선 작업이 없을 때만 AI를 돌리고, 다음 UL 도착 전에 끝낸다 | Orion (EuroSys'24), REEF (OSDI'22) 계열 | `i` |
| 보호 없음 | AI 비율 100%, 우선순위 같음 | 기본 MPS | `s100` |
| **Antiphase** | 2장 | – | `vf` |

비교 대상은 모두 우리 코드 위에서 그 방식의 동작을 구현한 것이다. 해당 논문의 코드를 돌린 것이 아니므로
"YinYangRAN보다 낫다"가 아니라 "부하 따라 비율을 바꾸는 방식보다 낫다"로 써야 한다.

재는 값:

- **AI 처리량**: 200 ms 안에 끝난 요청의 prompt token 수(초당).
- **L1 놓침**: 기존 수신기 결과가 L1 마감(4.0 ms)을 넘긴 TB의 비율.
- **복구 유지율**: 복구 마감 안에 NRx가 살린 TB 수를 같은 시드의 AI 없는 실행과 비교한 비율.
- **NRx 제때 완료**: 실행한 NRx 중 복구 마감 안에 끝난 비율.

## 2. v13에서 바뀐 Antiphase

v7–v12의 규칙은 "돌고 있는 NRx가 AI 옆에서도 복구 마감 안에 끝나는가"만 봤다. v13 첫 실행에서 두 가지를 확인했다.

**(1) 낮은 우선순위가 강한 기준선이다.** AI를 MPS 낮은 우선순위로 두면 고정 비율만 쓸 때보다 무선 쪽이 덜
느려진다. 16셀·전 부하·AI 제공 53k tokens/s에서 고정 30%는 20.0k에 복구 94.0%인데, 낮은 우선순위 + 30%는 17.6k에
96.6%, + 70%는 42.0k에 93.5%다. v7–v12의 Antiphase(22.6k, 97.0%)은 이 곡선과 거의 같은 선 위에 있었다.

**(2) 잃는 복구는 전부 "lane이 없어서"다.** 실패한 TB는 도착 후 3.9 ms(= 11.5 − 7.6) 안에 NRx를 시작해야 한다.
그때 lane 4개가 모두 차 있으면 그 TB는 버려진다. AI가 없어도 4%가 이렇게 버려진다(lane 4개, NRx 6.3 ms,
초당 243회 → Erlang-B 계산 5%와 맞음). AI가 NRx 옆에서 돌면 NRx가 6.3 ms에서 7.2–8.0 ms로 길어지고, lane이
늦게 비어서 다음 실패 TB가 시작 시각을 놓친다. AI 때문에 잃은 복구를 실행별로 분류하면, 보호 없음(고정
100%)을 빼고는 90% 이상이 "lane이 없어 시작 못 함"이고 "NRx가 늦게 끝남"은 10% 이하다(7장).

그래서 규칙을 이렇게 바꿨다.

| 항목 | v7–v12 | v13 |
|---|---|---|
| AI의 MPS 우선순위 | 무선과 같음, 비율 한도 70% | **낮은 우선순위**, 비율 한도 없음 |
| 기존 수신기 옆에서 허용하는 AI 단위 | 128 token만 | 128 / 512 / 1024 token 모두 |
| NRx 옆에서 AI | 그 NRx가 마감 안에 끝나면 허용 | 마감 조건 + **빈 lane이 3개 이상일 때만** 허용 |
| 겹침 한도(128/512/1024) | 10.1 / 9.8 / 10.3 ms | 8.1 / 8.5 / 8.7 ms (낮은 우선순위에서 다시 잼) |

**lane 여유 규칙**을 상황으로 설명하면 이렇다. GPU 0에서 NRx가 돌고 있고 다른 세 lane이 비어 있으면, 이 NRx가
1.5 ms 늦게 끝나도 다음 실패 TB는 다른 lane을 쓰면 되므로 AI를 같이 돌린다. 두 번째 NRx가 GPU 2에서 시작하면
빈 lane이 2개가 되고, controller는 GPU 0과 GPU 2에서 AI를 멈춘다(NRx가 없는 GPU 1, 3의 AI는 계속 돈다).
controller는 lane 상태를 루프마다(15–57 µs) 보므로 이 판단에 추가 비용이 없다.

낮은 우선순위에서 잰 시간(16셀, AI가 한 단위 크기로 계속 도는 실행, `v13_cal.sh`):

| AI | 기존 수신기 완료 p99 / p99.9 (ms) | NRx 실행 p50 / p99 (ms) |
|---|---|---|
| 없음 | 2.92 / 3.23 | 6.28 / 6.79 |
| 70% 비율, 128 token | 3.25 / 3.46 | 7.37 / 8.09 |
| 70% 비율, 1024 token | 3.96 / 4.52 | 8.39 / 9.43 |
| 낮은 우선순위 + 70%, 128 token | 3.19 / 3.56 | 7.25 / 7.56 |
| 낮은 우선순위 + 70%, 1024 token | 3.30 / 4.29 | 7.60 / 8.04 |
| 낮은 우선순위, 한도 없음, 1024 token | 3.44 / 4.05 | 7.89 / 8.51 |

AI 입장 제어에는 여유를 뒀다: 요청이 시간 제한의 75% 안에 끝난다고 예측될 때만 받는다(모든 방식 공통,
`--ai-admission-fraction 0.75`). 여유가 없으면 과부하에서 받은 요청의 20%가 제한을 넘긴다.

- **같은 AI 처리량에서.** 낮은 우선순위 + 70%는 41.9k로 AI는 비슷하지만 복구를 6.6% 잃는다. Antiphase는
  2.6%를 잃는다(2.5배 적음).
- **과부하(106k).** 모든 방식의 처리량이 줄어든다. 입장 제어가 짧은 요청 위주로 받게 되어 token당 효율이
  떨어지기 때문이다. Antiphase는 28.1k에 97.8%, 낮은 우선순위 + 70%는 28.6k에 92.8%다.
- **유휴 시간만.** GPU에 무선 작업이 없을 때만 AI를 돌리면 복구는 99.7%를 지키지만 AI는 4.7k다. 셀 4개와
  NRx가 GPU를 거의 계속 쓰기 때문이다.

시드 범위(AI 53k): Antiphase AI 37.4–41.9k, 복구 97.1–97.6%; 고정 10% 5.1–5.5k, 96.8–97.7%; 낮은 우선순위 + 30%
17.6–17.8k, 96.2–96.9%; + 70% 39.7–44.3k, 92.5–94.4%.

## 4. 부하가 바뀔 때: 교대, 무작위 계단, 버스트 (16셀, AI 53k 제공)

### 4.1 전 부하와 절반 부하가 번갈아 올 때

2초마다 "모든 셀 활성"과 "셀마다 확률 0.5로 활성"이 번갈아 온다(20초 실행, 시드 3).
그림: `v13_frontier_phase2s_*.png`, 교대 간격별 `v13_phase_*.png`.

| 방식 | AI 처리량 (시드 범위) | 복구 유지율 (시드 범위) | L1 놓침 |

| **Antiphase** | 27.2k | 96.1% | 0.034% (3.47 ms) |
| 고정 10% | 5.1k | 99.3% | 0.023% |
| 고정 30% | 20.0k | 94.1% | 0.098% (3.98 ms) |
| 고정 50% | 34.8k | 90.0% | 0.226% (4.19 ms) |
| 낮은 우선순위 + 30% | 17.0k | 96.1% | 0.044% |
| 낮은 우선순위 + 50% | 31.8k | 94.4% | 0.050% |
| 낮은 우선순위 + 70% | 40.5k | 94.2% | 0.039% |
| 낮은 우선순위, 한도 없음 | 46.6k | 92.8% | 0.091% (3.97 ms) |

- L1: Antiphase는 AI 없는 실행 수준(0.034%). 우선순위 없는 고정 30%·50%는 0.10%·0.23%로 3–7배다.
- AI: 같은 복구(96.1%)의 낮은 우선순위 + 30%보다 1.6배. 고정 10%는 복구를 99.3% 지키므로 "같은 복구 수준"
  비교가 아니다(Antiphase가 3.2%p 더 잃음).

### 8.2 AI 조각 길이 (16셀 전 부하, 시드 1·2, 같은 job 안에서 다시 잼)

| 조각 한도 | lane 여유 3 | lane 여유 2 |
|---|---|---|
| 4.0 ms (sweep에 쓴 값) | 40.2k / 98.0% | 41.2k / 97.7% |
| 2.5 ms | 40.1k / 98.8% | 41.7k / 98.2% |
| 1.5 ms | 36.0k / 98.8% | 37.7k / 98.2% |

조각을 2.5 ms로 줄이면 AI는 같고 복구가 0.5–0.8%p 오른다. 1.5 ms는 1024 token 단위를 못 써서 AI가 10% 준다.
차이가 실행 간 변동(같은 시드·같은 설정이 job에 따라 97.4%와 98.0%)과 같은 크기라 sweep 값은 4.0 ms 그대로
두었다. 다음에 다시 돌린다면 2.5 ms가 낫다.

쓰면 안 된다:

| 문장 | 이유 |
|---|---|
| "YinYangRAN·SMEC·Orion보다 낫다" | 그 방식을 우리 코드에 구현해 비교했다. 원본 시스템을 돌리지 않았다 |
| "L1 마감을 보장한다" | 놓침 0.03–0.04%는 AI 없는 실행과 같다는 뜻이다. 프로토타입의 값이고 한도가 아니다 |
| "모든 규모에서 L1을 더 잘 지킨다" | 48셀·셀 버스트는 AI 없이도 0.09–0.83%이고 Antiphase가 낫지 않다 |
| "GPU 수와 무관하게 낫다" | GPU 1장에서는 낮은 우선순위 + 70%와 같다 |
| "어떤 조건에서도 AI가 가장 많다" | 낮은 우선순위·한도 없음이 48.4k로 더 많다(복구 92.0%). 우위는 "복구를 지키면서"다 |
| "고정 10%의 5배", "부하 따라 비율의 1.17배", "27.4k @ 98.6%" | v12 규칙과 우선순위 없는 기준선의 값 |
| "lane 여유 규칙이 최적이다" | 여유 수(R=3)는 lane 4개에서 손으로 정했다. 조각 길이도 2.5 ms가 조금 낫다 |

남은 약점:

1. 시드 2–3개, 실행 10–40초. 헤드라인(2초 교대)과 전 부하만 시드 3.
2. 비교 대상에 부하 예측기가 없다(전환 비용 0, 부하를 바로 앎은 비교 대상에 유리한 가정).
3. lane 여유 수와 단위 크기 규칙을 GPU 수·GPU당 셀 수마다 손으로 정했다.
4. 입력은 미리 만든 IQ(합성 채널)이고 L2가 없다. 복구 마감 11.5 ms의 HARQ 영향은 계산만 했다.
5. 이 노드에서는 같은 설정의 복구 유지율이 job에 따라 0.5%p쯤 움직인다.

- 한 번에 2시간 넘게 걸리는 명령은 나눠서 돌린다. `run_matrix.sh`는 같은 job에서 끝난 실행을 건너뛴다.
- 실행 이름은 `<tag><seed>n`(AI 없음)과 `<tag><seed>r<AI 부하><방식>`이다. tag: `q` AI 부하, `ha/hb/hc` 교대
  0.2/2/5초, `st` 계단, `wa–wd` 약한 셀 0/2/6/8, `ga/gb` GPU 1/2장, `ca/cb` 32/48셀, `da` 20셀, `ba/bc` 32셀 셀
  버스트, `bd/be` 16셀 셀 버스트, `ab` AI 버스트. 방식: `vf` Antiphase, `sP` 고정 P%, `pP` 낮은 우선순위 + P%,
  `dAxBlN`/`eAxBlN` 부하 따라 비율(e는 낮은 우선순위, N은 늦게 아는 주기 수), `i` 유휴 시간만.
